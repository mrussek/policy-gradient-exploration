What is eBPF?

eBPF (extended Berkeley Packet Filter) lets you run sandboxed programs inside the Linux kernel without changing kernel source code or loading kernel modules. Think of it as JavaScript for the kernel — a safe, portable way to extend what the kernel does at runtime.

Originally designed for packet filtering (the "BPF" in tcpdump), it evolved into a general-purpose in-kernel virtual machine. Today eBPF powers production systems at Meta, Google, Cloudflare, Netflix, and virtually every major cloud provider.

Key insight: Instead of asking the kernel to send data to userspace so you can analyze it, eBPF lets you bring your analysis to where the data already lives — inside the kernel. This eliminates copying overhead and enables microsecond-level instrumentation.

Why eBPF Matters

Traditionally, extending the kernel meant one of three painful options:

Modify kernel source

Submit a patch upstream, wait years for adoption across distros. Not practical for custom logic.

Write a kernel module

Full kernel access but no safety guarantees. A bug crashes the entire machine. Maintenance nightmare across kernel versions.

Stay in userspace

Safe, but every packet/event must cross the kernel-user boundary. High overhead for high-frequency operations.

eBPF gives you a fourth option that combines the best of all three:

eBPF programs

Run inside the kernel with native speed. The verifier guarantees safety — no crashes, no infinite loops, no unauthorized memory access. Programs are portable across kernel versions via CO-RE (Compile Once – Run Everywhere).

<100ns per-packet XDP processing
0% crash risk (verifier-checked)
1M+ events/sec tracing throughput

The flow is: you write C (or Rust) code, compile it to eBPF bytecode, the kernel verifier checks it for safety, the JIT compiler turns it into native machine code, and it runs at nearly bare-metal speed whenever its hook point fires.

The Verifier

The verifier is the gatekeeper. Every eBPF program must pass its checks before the kernel will run it. This is what makes eBPF safe to run in kernel space.

The verifier performs two passes:

  1. DAG check: Ensures the control flow graph is a directed acyclic graph (no unreachable instructions, no loops that can't be proven to terminate).
  2. State simulation: Walks every possible execution path, tracking register types and value ranges. Every memory access must be proven safe.

Here's what the verifier rejects:

Unbounded loops Must have provable upper bound (bounded loops OK since 5.3)
Out-of-bounds access Every pointer dereference verified at load time
Uninitialized reads All register/stack reads must follow a write
Invalid helper calls Only approved helpers for the program type
Type violations Can't use a scalar as a pointer or vice versa
Stack overflow 512-byte stack limit is strictly enforced

Maps & Data Structures

eBPF maps are key-value stores that live in kernel memory. They're the primary way eBPF programs share data with each other and with userspace. Maps persist across program invocations — they're the program's "memory."

Common map types:

BPF_MAP_TYPE_HASH

General-purpose hash table. Arbitrary keys/values. Most common map type.

BPF_MAP_TYPE_ARRAY

Fixed-size array indexed by integer. O(1) lookup. Pre-allocated, can't delete entries.

BPF_MAP_TYPE_RINGBUF

Lock-free ring buffer for streaming events to userspace. Replaced perf buffers in modern code.

BPF_MAP_TYPE_LRU_HASH

Hash table with LRU eviction. Automatically discards old entries when full. Great for connection tracking.

BPF_MAP_TYPE_PERCPU_HASH

Per-CPU hash table. Each CPU has its own copy — no locking needed. Ideal for counters.

BPF_MAP_TYPE_PROG_ARRAY

Array of eBPF programs for tail calls. Enables program chaining and dispatch tables.

Example: Tracing Syscalls

    

      Let's trace every openat() syscall to see which files processes are opening.
      This is one of the simplest and most useful eBPF programs you can write.
    

    

      

        C (eBPF)
        opensnoop.bpf.c
      

      
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>

// Map: share data between kernel eBPF and userspace
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

// Event structure sent to userspace
struct event {
    u32 pid;
    u32 uid;
    char comm[16];
    char filename[256];
};

// Attach to the openat() syscall entry
SEC("tracepoint/syscalls/sys_enter_openat")
int trace_openat(struct trace_event_raw_sys_enter *ctx)
{
    struct event *e;

    // Reserve space in the ring buffer
    e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e) return 0;

    // Fill in event data
    e->pid = bpf_get_current_pid_tgid() >> 32;
    e->uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));
    bpf_probe_read_user_str(&e->filename, sizeof(e->filename),
                            (void *)ctx->args[1]);

    // Submit event to userspace
    bpf_ringbuf_submit(e, 0);
    return 0;
}

    


    

      The userspace loader opens the ring buffer and reads events:
    

    

      

        Python
        opensnoop.py
      

      
from bcc import BPF

b = BPF(src_file="opensnoop.bpf.c")

# Attach and print events
print(f"{'PID':<8} {'COMM':<16} {'FILE'}")

def print_event(cpu, data, size):
    event = b["events"].event(data)
    print(f"{event.pid:8} {event.comm:16} {event.filename}")

b["events"].open_ring_buffer(print_event)
while True:
    b.ring_buffer_consume()

Example: XDP Packet Filter

    

      XDP (eXpress Data Path) lets you process packets before the kernel's networking
      stack even sees them. This is the fastest programmable packet processing available on
      Linux — millions of packets per second on a single core.
    

    

      

        C (eBPF)
        xdp_firewall.bpf.c
      

      
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <bpf/bpf_helpers.h>

// Map of blocked IP addresses
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);          // IPv4 address
    __type(value, __u64);        // drop counter
    __uint(max_entries, 10000);
} blocklist SEC(".maps");

// Packet counters
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __type(key, __u32);
    __type(value, __u64);
    __uint(max_entries, 3);  // 0=pass, 1=drop, 2=total
} counters SEC(".maps");

SEC("xdp")
int xdp_firewall(struct xdp_md *ctx)
{
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    // Parse Ethernet header
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;

    // Only process IPv4
    if (eth->h_proto != __constant_htons(ETH_P_IP))
        return XDP_PASS;

    // Parse IP header
    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;

    // Check source IP against blocklist
    __u32 src_ip = ip->saddr;
    __u64 *blocked = bpf_map_lookup_elem(&blocklist, &src_ip);

    __u32 key_total = 2;
    __u64 *total = bpf_map_lookup_elem(&counters, &key_total);
    if (total) (*total)++;

    if (blocked) {
        // IP is in blocklist — drop and count
        (*blocked)++;
        __u32 key_drop = 1;
        __u64 *drops = bpf_map_lookup_elem(&counters, &key_drop);
        if (drops) (*drops)++;
        return XDP_DROP;  // packet never reaches the stack
    }

    __u32 key_pass = 0;
    __u64 *passes = bpf_map_lookup_elem(&counters, &key_pass);
    if (passes) (*passes)++;
    return XDP_PASS;
}

Example: Security Enforcement

    

      LSM (Linux Security Module) BPF programs let you write custom security policies.
      Here's a program that blocks processes from executing files in /tmp:
    

    

      

        C (eBPF)
        no_tmp_exec.bpf.c
      

      
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>

// Attach to the bprm_check_security LSM hook
// This runs before every execve()
SEC("lsm/bprm_check_security")
int BPF_PROG(no_tmp_exec, struct linux_binprm *bprm, int ret)
{
    // If a prior LSM already denied, respect that
    if (ret != 0)
        return ret;

    char path[256];
    int err;

    // Read the file path being executed
    struct file *file = bprm->file;
    struct path *f_path = &file->f_path;
    err = bpf_d_path(f_path, path, sizeof(path));
    if (err < 0)
        return 0;  // can't read path, allow

    // Check if path starts with /tmp/
    if (path[0] == '/' && path[1] == 't' &&
        path[2] == 'm' && path[3] == 'p' &&
        path[4] == '/') {
        bpf_printk("BLOCKED exec from /tmp: %s", path);
        return -EPERM;  // deny execution
    }

    return 0;  // allow
}

    


    

      Real-world usage: Projects like Cilium Tetragon use
      LSM BPF to enforce security policies in Kubernetes clusters — blocking
      unauthorized process execution, file access, and network connections at the
      kernel level with sub-microsecond latency.
    

  


  
  

    
Tooling Ecosystem

    

      You don't have to write raw eBPF bytecode. A rich ecosystem of tools and frameworks
      makes eBPF accessible:
    

    

      
    


    

      

        
libbpf

        
The canonical C library. Provides CO-RE support, skeleton generation, and low-level control. Used by most production systems.

        C
      

      

        
BCC

        
BPF Compiler Collection. Python/Lua bindings for rapid prototyping. Compiles C to BPF at runtime. Great for one-off tools.

        Python
      

      

        
bpftool

        
Swiss-army knife CLI for inspecting loaded programs, maps, links, and BTF type info. Essential for debugging.

        CLI
      

      

        
Cilium

        
Kubernetes networking, observability, and security powered by eBPF. Replaces kube-proxy, implements network policies.

        K8s
      

      

        
bpftrace

        
High-level tracing language (like awk for eBPF). One-liners for quick kernel analysis.

        Tracing
      

      

        
Aya

        
Write eBPF programs in pure Rust. No C toolchain needed. Growing ecosystem with strong type safety.

        Rust

Limitations & Gotchas

    
eBPF is powerful, but it's not magic. Understand these constraints before diving in:


    

      

        
Stack Size

        
512 bytes only. No heap allocation. Large buffers must use maps or per-CPU arrays. This is the most common frustration for beginners.

      

      

        
No Sleeping

        
eBPF programs can't sleep, block, or wait. No mutexes, no I/O, no sleeping memory allocations. Everything must complete in bounded time.

      

      

        
Verifier Complexity

        
Large programs can hit verifier limits. The verifier tracks state for every path, so deeply branching code may be rejected as "too complex."

      

      

        
Kernel Version Deps

        
New features require new kernels. CO-RE helps with portability, but you still can't use features your kernel doesn't have.

      

      

        
Helper Limitations

        
You can only call approved helper functions. No arbitrary kernel function calls (though kfuncs are relaxing this in newer kernels).

      

      

        
Debugging

        
No printf-debugging (though bpf_printk exists). No GDB. Verifier error messages can be cryptic. Debugging is the hardest part of eBPF development.

      

    

  


  
  

    
The Future of eBPF

    
eBPF is evolving rapidly. Here's what's on the horizon:

    
    
      
  • 
        eBPF on Windows: Microsoft is bringing eBPF to Windows via the
        ebpf-for-windows project. Cross-platform eBPF is becoming real.
      
    • 
      
  • 
        kfuncs: Kernel functions are being exposed as stable, typed APIs
        for eBPF programs, gradually replacing the fixed helper set.
      
    • 
      
  • 
        BPF Arena: Shared memory regions between eBPF and userspace,
        enabling more complex data structures and zero-copy communication.
      
    • 
      
  • 
        Scheduling: sched_ext allows writing CPU schedulers as eBPF
        programs — hot-swapping scheduling algorithms at runtime.
      
    • 
      
  • 
        HID-BPF: Programmable human interface devices. Fix buggy USB
        devices with eBPF instead of kernel patches.
      
    • 
      
  • 
        Networking 2.0: More of the networking stack is becoming
        programmable — from socket-level policy to full L4 load balancing.
      
    • 
    


    

      eBPF is on track to become the standard mechanism for runtime kernel extension.
      If you work with Linux in any capacity — infrastructure, networking, security,
      or performance — eBPF is worth learning. The kernel is becoming programmable,
      and eBPF is the programming model.
